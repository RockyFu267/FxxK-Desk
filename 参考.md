# 1. Project Identity

## 1.1 Name & Philosophy

FxxK-Limits is an independent open-source project focused on breaking unnecessary software and technology barriers through computer vision, local AI, and intelligent desktop automation.

- Freedom of technology.

- Local-first AI.
- Software interoperability.
- Practical engineering.

Our philosophy:

> Technology should empower people, not restrict them.

> The name has an attitude. The mission has a purpose.

## 1.2 Project Vision

Build a general-purpose desktop automation framework that allows AI to observe, understand, and interact with graphical applications.

Traditional automation relies heavily on application-specific APIs, SDKs, DOM structures, or predefined UI selectors.

FxxK-Limits explores a different approach:

**Visual Perception + Local AI + Intelligent RPA**

Instead of requiring every application to expose an automation API, the framework uses the visual interface as an interaction layer.

The long-term goal is to provide a reusable automation infrastructure that can work with different desktop applications.

Target Application is the first application scenario, not the entire project.

# 2. Project Objectives

The project has five primary objectives.

## 2.1 Visual Perception

Build a computer vision pipeline capable of continuously observing desktop applications.

Capabilities:

- Screen capture.
- Window detection.
- Region-of-interest detection.
- OCR.
- UI element recognition.
- Visual change detection.
- Screenshot comparison.
- Visual state tracking.

## 2.2 Local AI Intelligence

Use locally deployed AI models to understand desktop interfaces.

Capabilities:

- Visual understanding.
- Text recognition correction.
- UI semantic interpretation.
- Message classification.
- Context extraction.
- Visual grounding.
- Action planning.

The framework should support different local models and OpenAI-compatible inference endpoints.

Model providers should be configurable rather than hardcoded.

## 2.3 Custom RPA Engine

Develop an independent desktop automation engine.

Capabilities:

- Mouse control.
- Keyboard control.
- Window management.
- Scrolling.
- UI element positioning.
- Action execution.
- Execution verification.
- Error recovery.
- Task scheduling.

The automation engine must support both visual-coordinate interaction and native Windows accessibility interfaces.

## 2.4 Continuous Observation

Unlike traditional task-driven Computer Use Agents, FxxK-Limits should emphasize continuous observation and event-driven automation.

The intended workflow:

1. Observe the desktop.
2. Detect screen changes.
3. Identify relevant visual regions.
4. Extract information.
5. Compare with previous observations.
6. Generate structured events.
7. Persist events.
8. Recover from interruptions.

This is a major architectural direction of the project.

## 2.5 Extensibility

The core framework must remain independent of individual applications.

Application-specific functionality must be implemented through adapters.

Examples:

- Target Desktop Application Adapter.
- Browser Adapter.
- Windows Application Adapter.
- Other messaging application adapters.

Adding a new application should not require rewriting the core perception or automation engine.

# 3. Initial Application: Target Desktop Application

## 3.1 Why Target Application?

Target Application is the first target application because it represents a typical closed desktop software ecosystem.

Its graphical interface provides a practical environment for validating visual perception, OCR, continuous monitoring, and RPA automation.

The initial target should offer representative desktop workflows for controlled testing.

The project should document tested capabilities and their limitations.

However:

**FxxK-Limits is not a single-application project.**

The core architecture must not depend on application-specific implementations.

## 3.2 Initial Functional Scope

The initial Target Application adapter should focus on desktop visual observation.

Primary capabilities:

- Detect the Target Application desktop window.
- Identify the active conversation.
- Identify the visible chat region.
- Recognize visible message bubbles.
- Extract message text.
- Identify visible sender information where available.
- Recognize timestamps where available.
- Identify images, files, voice messages, and other message types.
- Detect changes in the conversation view.
- Maintain incremental observation records.
- Avoid unnecessary duplicate records.

Secondary capabilities:

- Navigate between conversations.
- Scroll through visible history.
- Recover the previous observation state.
- Detect unexpected UI changes.
- Export structured observation records.

The initial milestone is not guaranteed full message acquisition.

The first objective is to establish a reliable visual observation pipeline.

## 3.3 Data Accuracy

Visual acquisition has inherent limitations.

The framework must explicitly distinguish:

- Successfully recognized content.
- Partially recognized content.
- Uncertain sender identity.
- Uncertain timestamps.
- Duplicate observations.
- Potentially missing content.

Never silently convert uncertain visual recognition into verified facts.

Every observation should retain its confidence score and original screenshot reference when available.

## 4.2 Perception Layer

Responsibilities:

- Capture desktop frames.
- Detect active windows.
- Identify relevant visual regions.
- Perform OCR.
- Detect visual differences.
- Normalize visual information.

Potential technologies:

| Technology | Purpose |
|---|---|
| Windows Desktop Duplication API | High-performance screen capture |
| DXGI | Windows graphics capture |
| PaddleOCR | Text recognition |
| OpenCV | Image processing and comparison |
| OmniParser | GUI element parsing |
| Local VLM | Visual semantic understanding |

The system should avoid sending every screenshot to a large VLM.

Prefer a layered pipeline:

Screen Capture → Change Detection → OCR → Target Region Extraction → VLM when necessary.

This reduces inference cost and improves responsiveness.

## 4.3 Intelligence Layer

Responsibilities:

- Interpret OCR results.
- Understand visual context.
- Identify message structures.
- Resolve uncertain recognition.
- Determine whether further observation is necessary.
- Produce structured information.

Potential model families:

- Qwen-VL.
- Other locally deployed vision-language models.
- OpenAI-compatible multimodal endpoints.

All model configuration must be externalized.

Never hardcode API keys, model endpoints, or credentials.

## 4.4 Automation Layer

Responsibilities:

- Window interaction.
- Mouse and keyboard control.
- Scrolling.
- UI navigation.
- Action sequencing.
- Execution verification.

Potential technologies:

- Windows UI Automation.
- pywinauto.
- Win32 APIs.
- PyAutoGUI.
- UIA-compatible libraries.

Actions must be state-aware.

Do not assume that an action succeeded simply because a mouse or keyboard event was issued.

The engine must verify the resulting visual state.

## 4.5 Event Processing Layer

All recognized observations should be converted into structured events.

Suggested event schema:

```json
{
  "event_id": "uuid",
  "application": "target_app",
  "conversation": "conversation_identifier",
  "sender": "recognized_sender",
  "content": "recognized_content",
  "content_type": "text",
  "timestamp": null,
  "observed_at": "ISO-8601",
  "confidence": 0.96,
  "source": "screen_ocr",
  "screenshot_reference": null,
  "verification_status": "unverified"
}
```

Important:

- `observed_at` represents when the system captured the information.
- `timestamp` represents the application-displayed message time.
- They must never be treated as interchangeable.
- Confidence values must be traceable to actual recognition results.
- The system must preserve uncertainty.
- Deduplication must not incorrectly merge two identical messages.

# 8. Engineering Principles

All AI Coding Agents contributing to this repository must follow these principles.

## 8.1 Modular Design

Do not put all functionality into a single Python script.

Separate:

- Screen capture.
- OCR.
- VLM inference.
- Visual parsing.
- RPA execution.
- Application adapters.
- Event processing.
- Storage.

Each module must have a clear responsibility.

## 8.2 Local-First

Prioritize local processing.

Screenshots, OCR results, and application data should remain on the local machine by default.

Cloud inference must be optional and explicitly configured.

Never upload screenshots or conversation content to an external service without explicit user configuration.

## 8.3 Reliability Over Intelligence

A simple OCR result with traceable provenance is preferable to an elaborate but unverifiable VLM interpretation.

The framework should:

- Preserve original observations.
- Track confidence.
- Detect uncertainty.
- Avoid inventing missing information.
- Verify automation actions.
- Record failures.

## 8.4 Performance

Do not invoke expensive VLM inference on every screen frame.

Use:

- Frame sampling.
- Change detection.
- Region-of-interest processing.
- OCR-first processing.
- Conditional VLM inference.
- Asynchronous task execution.
- Bounded queues.

## 8.5 Maintainability

- Use type hints.
- Write unit tests.
- Document public interfaces.
- Avoid unnecessary dependencies.
- Keep configuration external.
- Use meaningful commit messages.
- Maintain backward compatibility where practical.

# 9. Security, Compliance & Boundaries

FxxK-Limits is a general-purpose desktop automation framework.

The project must distinguish between legitimate desktop automation and unauthorized access to application internals.

The initial Target Application implementation should prioritize visible-screen acquisition and ordinary desktop automation.

The initial implementation must not depend on:

- DLL Injection into Target Application.
- Runtime modification of Target Application internals.
- Bypassing application authentication.
- Decrypting protected application databases.
- Circumventing access controls.

The use of screenshots, OCR, VLM, and Windows UI Automation does not automatically grant permission to collect or process another person's communications.

All testing must use authorized accounts, authorized test data, and appropriate participant consent.

The project must not promise that any automation technique is immune to platform restrictions or account enforcement.
